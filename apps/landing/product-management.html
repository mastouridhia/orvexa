How it was planned, prioritized, and shipped.

Orvexa is a real-time QR ordering stack for dine-in restaurants in Tunisia. Customers scan a table QR code, browse a trilingual menu, and place orders directly from their phone. The kitchen sees tickets instantly. The waiter sees which tables need attention. The owner sees live revenue and table activity on a dashboard.

Users and Their Jobs

Customer

  • Browse menu in AR / FR / EN
  • Place an order without a waiter
  • Track order status live
  • Call the waiter when needed
  • Request the bill when done

Kitchen Staff

  • See tickets the moment they land
  • Know how long each ticket has waited
  • Advance tickets in one tap
  • Glanceable from across the kitchen

Waiter

  • Floor map — every table's state at a glance
  • Call-waiter and bill-request alerts
  • Take payment and close a table
  • Mark dishes as passed to table

Owner / Admin

  • Edit trilingual menu with variant pricing
  • Live dashboard — revenue, top items, tables
  • Manage staff accounts and roles
  • Print QR codes for every table

Roadmap — What We Built and in What Order

Phases 0–3

Foundation

Shared TypeScript package (@orvexa/shared) with all domain types and Zod schemas, PostgreSQL schema with Drizzle migrations, a structured API layer (routes → services → repositories), and a real-time bus over Socket.io.

Built first because every subsequent phase depended on it being typed, validated, and consistent across all four apps. Skipped CI/CD, Husky, and conventional commits — personal project, manual deploy.

Phases 4–9

API Layer

Auth (JWT + refresh rotation), restaurant config, tables, menu with variant groups, orders with a state-machine status flow, payments (cash settled, card stubbed), and WebSocket event emission for every state change.

Built and verified before any frontend touched it. The variant group model (1 dish + price-delta variants) was validated against the Capitol menu before committing — no flattening into hundreds of SKUs.

Phases 10–13

The Four Apps

Customer app first — no orders without it. Kitchen and waiter apps second — they close the loop. Admin app last — configuration layer, needed before launch, not before the system works.

All functional before the visual redesign pass. Data layer (API clients, sockets, stores, i18n, variant selection) was preserved through the redesign entirely.

Phase 18

Saffron-Hospitality Redesign

Full visual port from the design handoff onto all four apps. Warm-paper base (#FAF8F4), saffron accent (#D97A2C), Newsreader Italic for headlines, Geist Mono for prices and reference codes. Each app tuned to its context: customer warm and inviting, kitchen dark and high-contrast, waiter and admin cool-light and functional.

Phases 19–22

First Client + Stability

Cashier role and counter-payment flow for Capitol. Post-bill customer feedback (1–5 stars + comment). Per-dish prep time with ETA on customer tracking and kitchen tickets. Table floor-plan editor with drag-and-drop zone assignment. Mixed-section order split (bar vs. kitchen). End-of-day close. Shared table cart synced over WebSocket.

Customer accounts By design. QR → session is the model. Accounts add friction that kills the no-login pitch.
Multi-currency Tunisia-only for now. TND hardcoded. Multi-currency is complexity for a problem that doesn't exist yet.
Per-item order status Café-scale kitchens prepare orders whole. No station split needed yet.
Redis pub/sub adapter Single-instance API. The RealtimeBus abstraction makes the swap local when horizontal scaling lands.
CI/CD pipeline Personal project. Manual docker compose up until a team warrants it.

Tailwind / CSS-in-JS Plain CSS with custom properties was already the de-facto choice. Rewriting working UI for no functional gain.
Reservations Net-new surface. Not designed, not needed for Capitol's go-live.
Audit log viewer The audit_log table exists but nothing writes to it yet. A viewer over an empty table is misleading.
Multi-restaurant tenancy Single-tenant until post-exam period. JWT already carries restaurantId — the scoping work is isolated when needed.

MVP — First Client Go-Live

Client: Capitol — a Tunisian café/restaurant in Tunis.
Deadline: 2026-05-16.
Language priority: French-primary, Arabic for mains, English available.

The Capitol menu has variant-priced dishes (pizza sizes), bread × filling matrices, and multi-select flavor choices. The variant group model — 1 dish + variant groups with price deltas — was validated against the Capitol seed data before committing to it.

Live means: real QR codes on real tables, real staff trained on their apps, real customers placing real orders, cash payment via waiter, and the owner watching the dashboard. Deployed at orvexa.tn on an OVH VPS with Let's Encrypt certificates for all five hostnames.

Key Product Decisions

No customer accounts — ever

The customer experience is scan → order → pay → done. Accounts add a login screen, password recovery, and session persistence — none of which makes the dining experience better. Users don't want to create an account to order a coffee. This is a constraint, not a limitation.

Variants, not SKUs

For a menu like Capitol's, we model 1 dish + variant groups with price deltas — not 250 separate line items. Flatten only when items are named recipes with genuinely different compositions. This keeps the menu editor usable and the order data meaningful.

Hold-to-bump on the kitchen board

Kitchen staff advance ticket status by holding a button for 600ms — not tapping. Prevents accidental status advances on a greasy touchscreen in a hot kitchen. Deliberate UX decision, not a missing tap handler.

Age-coded tickets

Tickets change color as they age: fresh (green) → cooking (neutral) → pushing (saffron) → late (red, throbbing shadow). Derived from createdAt + now, no configuration. The kitchen team reads the floor state at a glance from across the room.

Payments stub for non-cash

Card and mobile-pay methods create a pending payment record with a stub-<timestamp> provider reference. The real gateway swap is a one-line branch change in PaymentService.record. Cash-only for Capitol go-live.

Design handoff is the source of truth

The frontend handoff/ folder (HANDOFF.md + JSX surface files) is the canonical design reference. Where it conflicts with this document or TASKS.md, the handoff wins. Phase 18 was a direct port from those files — not an interpretation.

Key Questions We Had to Answer

Which features move the needle for Capitol specifically?
Speed from order placement to kitchen ticket. Fewer missed orders. Faster waiter response to calls. We built around these flows first — not analytics, not reporting, not audit logs.
What's the real problem — not what the owner says, but what they show?
The stated problem was "waiters forget orders." The actual problem was a broken information chain: kitchen doesn't know what was ordered until a waiter tells them, waiters don't know when food is ready until the kitchen shouts. Orvexa replaces verbal communication with a live data model that all three parties read simultaneously.
What should we build vs. buy vs. ignore?
Build: ordering flow, real-time bus, menu model, role-based auth. Buy (stub for now): payment gateway. Ignore: reservations, loyalty programs, inventory, fiscal integration — all real needs, none required to open the doors on day one.
Are we solving for today's user or tomorrow's?
Today's user is Capitol. We deliberately haven't built multi-tenant abstractions, multi-currency support, or internationalized fiscal requirements. The product generalizes when a second client signs — not before.
What's the cost of not shipping the variant group model?
High. Without it, Capitol's menu requires 250+ individual dishes to represent 15 dishes with options. The menu editor becomes unusable, the ordering flow confusing, and the order data meaningless for reports. Non-negotiable for MVP.
